## Summary

Hollow is a second example game (epic #245), set up the way moba is:

- `:hollow:game` is a KMP library on `udea.kotlin-multiplatform-render`. It has KSP (`udeaModule("Hollow")`
  gives `HollowUdeaRegistry`), the asset pipeline (`GameAssets.models.*`) and the bundled
  `levels/clearing.udealevel`.
- `:hollow:desktop` is a JVM launcher.
- There is no Android launcher, per the lead's decision.

**The clearing** is 184 entities, and every one has a `Transform3D` and a `NetId`:

- a textured 80 m ground;
- 70 trees in an inner and an outer ring;
- stones, stumps, logs, a fence, grass, bushes, flowers and mushrooms;
- one `Sunlight`.

It is written by `ClearingWriter` (`:hollow:desktop:udeaWriteClearing`), from a seeded layout
(`ClearingLayout`) in `hollow:desktop`'s test sources, through the game's own `LevelService`.

The models are 24 GLBs from the Kenney Nature Kit (CC0). `prepare.py` strips their
`KHR_materials_unlit` extension so they take the light, and recolours them. The ground is
generated by `make_ground.py` from seed 249. Licence and source are recorded:

- in `hollow/game/assets/models/nature/NOTICE.md` (zip SHA and a SHA for each file);
- in `hollow/game/assets/models/ground/NOTICE.md`;
- in `LICENSE`;
- in `docs/art-assets.md`.

**Drawing.** Scenery and Sunlight are plain `@Serializable` components with float fields, and no
Kool type appears in either. `ScenerySystem` is a `RenderSystem`, not a Fleks system:

- it gives each prop its `ModelRenderer`;
- it swaps the model when `Scenery.prop` changes;
- it copies the level's `Sunlight` into `ModelLight`, which carries a directional light, a shadow
  map and an ambient term.

`SkySystem` draws a gradient before the 3D pass. H1 uses a fixed camera (`HollowScene`).

**Multiplayer (the owner's ruling).** There are three tasks:

- `run` is a listen server on UDP 27025 plus a local player window.
- `runServer` is headless, with an optional tick limit `-Phollow.server.ticks=N`.
- `runClient --args="host [port]"` or `--args="join <host[:port]>"`.

`HollowServer` and `HollowClient` are written against `Transport` alone. So the in-process
`NetHarness` and a UDP socket are the same thing to them.

**Decision: which replication approach** (commented on #249). The static clearing is level content
that every machine loads. Replication binds the server's entities onto it by `NetId`, and the
replicated component is `Transform3D`. Anything the server spawns later reaches a client only
through replication. `HollowReplicaApplier` does three things:

- it creates entities it has not seen, under the server's `NetId`;
- it destroys only the entities it created;
- it writes the server's values over the level's.

No name was added to `net-components.lock`. A `dev.wildware.hollow` name sorts ahead of every moba
name, so adding one would renumber moba's wire ids and its replay fixtures.

**A surprise, now resolved.** On master before #246, `Transform3D` was all-`@Sim`. `udea-net`
writes no record for an entity whose components have nothing to say, so the replication test
failed with an empty replica store: "`client1's replica store ==> expected: <[0, 1, ... 183]> but
was: <[]>`". The artefact for that run is gone, so this is prose.

For a while this branch carried an interim fix inside Hollow: the generated replicator with its
`netMask` widened. #246 has now merged. Hollow uses `Transform3D.snapshotType()`, and the interim
replicator is deleted (commit `1fcf9e6`).

**A second surprise, and it is not this branch's to fix.** After #246, `RenderModule` gives every
`Transform3D` an internal, non-`@Serializable` `Interp3D` at its first tick end. So
`LevelService.saveNow` throws on any world that has run a tick:

    holds dev.wildware.udea.render.interp.Interp3D, which no generated level component list names

I reported it to the lead, and #246 is reopened for it. `ClearingLevelTest`'s resume test
therefore saves from an empty world that has run 50 ticks, and its comment names the reopen.

**Build and gate wiring:**

- `settings.gradle.kts` includes `hollow:game` and `hollow:desktop`.
- `ModuleGraphRules` gains `HOLLOW_PROJECTS` and `GAME_PROJECTS`.
- MG-005 and MG-013 cover Hollow's projects, and `governs()` covers `:hollow:*`.
- The root build takes its governed projects from `governs()`, so `udeaVerifyModuleGraph`,
  `udeaVerifyEditorAbsent` and the others run on Hollow.
- `udeaVerifyRelease` covers both launchers.
- `udeaVerifyNoLibGdx` scans Hollow's bytecode. The settings check in its test now reads
  `hollow:` too; without that, it failed on this branch.
- `udeaAssemble` stays the engine plus moba. The clean-build-budget CI job compares that task on a
  branch against its base, and adding a second game to it would read as the engine slowing down.
  The KDoc says so.
- `AGENTS.md` (module table, governed scope, levels) and `docs/module-graph.md` are updated.

**Left out on purpose:**

- no agent source set, `runEditor` or `gamebridge.json` (H7, #255);
- no player or camera rig (#250);
- no physics bodies on the trees (#247 makes that possible);
- no determinism-scan config for `:hollow:game`, because H1 has no simulation systems.

`HollowReplicaApplier` is close to moba's `ReplicaApplier`. The one real difference is a world that
already holds the level. Moving both into `udea-net` would be a separate change and is out of
scope here.
